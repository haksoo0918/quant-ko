# 테스트 및 코드 품질 규칙 (Testing & Quality Standards)

본 문서는 프로젝트의 테스트 전략, 정적 분석 요구사항 및 코드 품질 기준을 정의합니다.

## 1. 테스트 전략 및 테스트 피라미드

1. **단위 테스트 (빠르고 격리된 검증)**:
   - 순수 함수, 유틸리티, 도메인 비즈니스 로직, 상태 머신을 집중적으로 검증합니다.
   - 외부 네트워크 및 I/O 의존성은 모킹(Mock) 처리합니다.
2. **통합 테스트 (컴포넌트 및 API 검증)**:
   - 컨트롤러-서비스-데이터베이스 간 상호작용 또는 UI 컴포넌트 간 통합 동작을 검증합니다.
   - 테스트용 격리 데이터베이스나 모의 서버를 활용합니다.
3. **E2E(End-to-End) 테스트 (핵심 사용자 여정)**:
   - 로그인, 결제, 핵심 가치 흐름 등 실패 시 치명적인 시나리오를 자동화합니다.

---

## 2. 테스트 작성 원칙
 
1. **TDD(테스트 주도 개발) 사이클 적용**:
   - **Red (실패하는 테스트)**: 구현 전 요구사항을 만족하는 실패 테스트를 먼저 작성합니다.
   - **Green (최소 구현)**: 해당 테스트를 가장 빠르게 통과시키는 최소한의 코드를 작성합니다.
   - **Refactor (구조 개선)**: 테스트가 통과하는 상태를 유지하면서 가독성, 중복 제거, 모듈화를 개선합니다.
2. **AAA 패턴 준수**: 테스트 코드를 **준비(Arrange)**, **실행(Act)**, **검증(Assert)** 단계로 명확히 구분합니다:
   ```typescript
   it('세금이 포함된 주문 총액을 올바르게 계산해야 한다', () => {
     // Arrange (준비)
     const cart = [{ price: 100, qty: 2 }];
     // Act (실행)
     const total = calculateTotal(cart, 0.1);
     // Assert (검증)
     expect(total).toBe(220);
   });
   ```
3. **결정론적 격리성**: 테스트는 실행 순서에 영향을 받지 않아야 하며, 전역 가변 상태를 공유하지 않아야 합니다.
4. **설명적인 테스트 명명**: 상황과 기대 결과를 명확히 드러내는 테스트 이름을 부여합니다 (`<조건>일 때 <기대 동작>을 수행해야 한다`).

---

## 3. 정적 분석 및 빌드 검증

1. **언어별 공식 컨벤션 준수**: 해당 언어의 공식/표준 스타일 가이드(TS: camelCase/PascalCase, Python: PEP 8/snake_case, Go: Effective Go 등)와 관용적(Idiomatic) 패턴을 철저히 준수.
2. **린터 & 포맷터 필수 도입**: 프로젝트 초기화 시 표준 도구(Biome, Ruff 등)를 즉시 구성하고, '저장 시 자동 포맷' 및 커밋 전 린트 검사로 스타일 불일치 방지.
3. **엄격한 타입 검사**: 타입 검사기 경고(예: `tsc --noEmit`, `mypy`) 0개 유지.
4. **미사용 코드 정리**: 미사용 임포트, 디버깅용 콘솔 로그, 더미 코드 제거.

---

## 4. 완료 정의 (Definition of Done, DoD)

모든 기능 구현 및 버그 수정 완료 전 체크리스트:
- [ ] 변경 사항을 검증하는 단위/통합 테스트가 작성되고 모두 통과했는가?
- [ ] 린터 및 정적 타입 검사에서 에러가 발생하지 않는가?
- [ ] 전체 애플리케이션 빌드가 성공적으로 완료되는가?
- [ ] 관련 문서와 `PRD.md`가 최신 상태로 갱신되었는가?
