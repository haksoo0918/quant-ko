# Git 워크플로우 및 릴리즈 규칙 (Git Workflow & Release Standards)

본 문서는 이 저장소에서 사용하는 Git 커밋 규칙, 브랜치 전략 및 릴리즈 절차를 규정합니다.

## 1. 커밋 메시지 컨벤션

모든 커밋 메시지는 **한글 Conventional Commits** 규격을 따르며, 전면 한글로 작성합니다:

```
<타입>(<스코프>): <간결한 한글 요약>

[상세 한글 본문 (선택)]

[바닥글 (선택)]
```

### 한글 커밋 타입 (Types)
| 타입 | 영문 대응 | 용도 및 의미 | 작성 예시 |
| :--- | :--- | :--- | :--- |
| `기능` | `feat` | 새로운 기능 추가 | `기능(인증): 구글 OAuth2 로그인 연동` |
| `수정` | `fix` | 버그 및 오류 수정 | `수정(장바구니): 음수 수량 입력 방지` |
| `문서` | `docs` | 문서 작성 및 수정 | `문서(prd): 결제 데이터 스키마 명세 업데이트` |
| `개선` | `refactor` | 기능 변경 없는 순수 코드 구조 개선 | `개선(db): 커넥션 풀 싱글톤 분리` |
| `성능` | `perf` | 성능 최적화 및 쿼리 개선 | `성능(검색): 자동완성 쿼리 결과 인메모리 캐싱` |
| `테스트` | `test` | 테스트 코드 추가 또는 보강 | `테스트(api): 주문 결제 통합 테스트 추가` |
| `관리` | `chore` | 빌드, 의존성 패키지, 환경 설정 변경 | `관리(의존성): biome v1.9 버전 업데이트` |
| `스타일` | `style` | 코드 포맷팅, 세미콜론 등 스타일 수정 | `스타일(코드): 린터 포맷팅 규칙 일괄 적용` |

### 커밋 작성 규칙
- 커밋 타입, 스코프, 요약문, 상세 본문 모두 **한국어** 로 작성합니다.
- 요약문 끝에 마침표(`.`)를 찍지 않습니다.
- 한 커밋에는 하나의 논리적 변경만 담는 '원자적 커밋(Atomic Commit)'을 유지합니다.
- 무엇을 왜 변경했는지 명확하고 직관적으로 서술합니다.

## 2. 브랜치 전략 (최소 2개 브랜치 모델)

```
main (배포/릴리즈 - 항상 안정 상태 유지)
 ▲
 │ 검증 완료 후 직접 머지
dev  (일상 개발 - Antigravity 바이브코딩 작업 공간)
```

1. **`main`**: 배포 전용 브랜치(검증 완료된 코드 및 릴리즈 태그 관리).
2. **`dev`**: 일상 개발 브랜치(모든 기능 구현, 버그 수정, 리팩토링 커밋 공간).
3. **`try/<실험명>` (선택)**: 대규모 실험/프로토타입용 임시 브랜치.

## 3. 머지 및 검증 워크플로우

**커밋, 머지, 푸시는 각각 독립된 개별 단계** 로 엄격히 나누어 진행합니다:

1. **1단계: `dev` 커밋 (자율 로컬 커밋, 원격 푸시 엄격 금지)**:
   - `dev` 브랜치에서 원자적 커밋(한글 커밋 컨벤션)을 자율적으로 수행하고 즉시 중단.
   - **`dev` 브랜치의 원격(`origin/dev`) 푸시는 엄격히 금지** 됩니다 (`dev`는 순수 로컬 워크스페이스).
2. **2단계: `main` 머지 (사용자의 명시적 지시 및 승인 시에만)**:
   - 테스트 통과, 린터/타입 검사 0에러, PRD/CHANGELOG 반영 확인 후 사용자 승인을 얻어 머지 수행:
     ```bash
     git checkout main
     git merge dev --no-ff
     ```
3. **3단계: 원격 푸시 및 싱크 (`main` 브랜치 전용, 사용자 명시적 승인 시에만)**:
   - 원격 푸시 및 싱크는 **오직 `main` 브랜치에서만 허용** 됩니다.
   - 사용자의 명시적인 푸시 승인이 있을 때만 `origin/main`에 푸시.

### Git 훅 보호 장치 및 에이전트 가드레일 (`.githooks/`)
- **`dev` 브랜치 원격 푸시 물리적 원천 차단**: `.githooks/pre-push` 훅에서 푸시 대상에 `dev`가 포함되어 있으면 예외 없이 즉시 거부(`exit 1`)합니다 (`origin/dev` 푸시 불가).
- **`main` 머지 및 푸시 채팅 승인제**: 에이전트는 사용자가 대화창에서 명시적으로 지시/승인한 경우에만 `main` 머지 및 `origin/main` 푸시를 1회성으로 실행합니다.
- **단일 작업 즉시 중단(Single Instruction Discipline)**: `dev` 커밋 완료 후 머지나 푸시를 임의로 연속 실행하지 않고 즉시 멈춥니다.

## 4. 릴리즈 및 시맨틱 버저닝 (SemVer) 전략

**Semantic Versioning (SemVer)** 규칙 `vMAJOR.MINOR.PATCH` (`vX.Y.Z`)를 준수하며, 작업 성격에 따라 태그 발행 여부를 명확히 구분합니다:

| 변경 수준 | 작업 내용 | `main` 머지 여부 | 태그 생성 여부 |
| :--- | :--- | :---: | :---: |
| **Z (Patch)** | 오탈자, 단순 문서 수정, 리팩토링, 경미한 버그 수정 | **머지 & 푸시 O** | ❌ **태그 없음** (가볍고 빠르게 반영) |
| **Y (Minor)** | PRD 상의 새로운 기능 단위 완성, 주요 모듈 추가 | **머지 & 푸시 O** | 🏷️ **태그 생성** (`vX.Y.0`) |
| **X (Major)** | 아키텍처 전면 개편, 하위 호환성 단절 (Breaking Change) | **머지 & 푸시 O** | 🏷️ **태그 생성** (`vX.0.0`) |

### 태그 생성 원칙
1. **머지 빈도**: 안정화된 변경점은 `dev`에서 `main`으로 수시로 자유롭게 머지 및 푸시합니다.
2. **태그 발행 시점**: Git 태그는 **Y(새 기능 완성) 또는 X(대규모 개편) 시점에만** 생성합니다. 단순 패치나 문서 정리는 태그를 찍지 않습니다.
3. **사용자 승인**: 태그를 발행하고 원격 저장소에 푸시하기 전에는 반드시 사용자의 명시적 승인을 받습니다.
